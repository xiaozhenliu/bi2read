# ADR-0002：v0.5.0 可信内容派生契约

状态：Accepted（v0.5.0 实现边界；交付状态以路线图为准）
日期：2026-08-23
修订：2026-08-24，个人工具 MVP 收敛并完成候选实现
目标版本：v0.5.0
产品依据：内部 PRD 7.5（可信文字消费）
交互依据：[当前 Design Spec](../design/bi2read-design-spec.md)
当前实现基线：[Architecture 1.2](../architecture.md)

本次修订替代此前扩展出的复杂草案。它保留 PRD 已批准的四项可信内容、来源核对、独立失败、
单项重新生成和完整 provenance，但把实现收敛到个人工具真正需要的单进程、单 worker 模型。
本文是 v0.5.0 实现的架构决策。实现与 UI 验收事实以源码、测试、路线图和当前
Design Spec 为准。

## 背景

当前 Pipeline 持久化原始转写 Evidence，再由 `document` 生成原始稿、规则阅读稿和最终
Markdown；可选 `llm::refine_utterances` 仍以逐条对应的校正结果为主。这个结构保护了原始稿，
但不能表达 v0.5.0 所需的章节、默认摘要、重点、来源状态、长文覆盖校验、独立失败和单项
重新生成。

直接继续扩展 `full.md` 会把内容事实、生成规则和展示格式绑定在一起。反过来，为单机个人
工具建立 command ledger、attempt ledger、receipt、双副本 CAS、投影状态机和历史指针，又会
让调用者和恢复逻辑承担远大于产品价值的复杂度。

v0.5.0 已采用一个深的 `ContentResults` 模块：调用者只表达“生成初始结果”或“重新生成某一项”，
模块内部负责读取 Evidence、选择 recipe、调用本地模型、分块合并、校验、失败隔离和原子发布。
App 与 Markdown 都消费同一份结构化 current；Markdown 只是可重建的 Presentation。

## 决策

### 1. 外部 seam 只有执行和读取

以下是领域 interface；具体 Rust 文件与类型名可在 issue 中按现有代码收敛：

```text
ContentResults::execute(job, intent, cancel) -> Result<ContentSnapshotV1, ContentError>
ContentResults::current(job) -> Result<ContentViewV1, ContentError>

Intent
├── Initial
└── Regenerate
    ├── kind                 chapters | default_summary | highlights
    └── target               本次明确操作读取到的 ReadyGenerationTargetV1
```

`ContentViewV1` 是闭集 `Legacy | RawOnly { validated_evidence, current_issue } |
Current(ContentSnapshotV1)`；snapshot 由 `ContentCurrentV1` 和经过复核的
`ValidatedEvidenceViewV1` 组成。`RawOnly` 只用于带 marker 且 raw 有效、current 未生成或损坏的
任务。UI、renderer 和来源展开只消费 view，不自行打开或解释 `transcript.raw.json`；结构化
current 不重复保存原始文本。raw 本身无效返回 `ContentError`。

`execute` 隐藏以下 implementation：

- 定位并校验 `transcript.raw.json`，计算 Evidence descriptor；
- 读取任务创建时的初始内容计划；
- 组装标题、选中分 P 标题、邻近片段和术语上下文；
- 选择固定 recipe，完成长文分块、层级合并和覆盖校验；
- 通过内部 `GenerationPort` 调用本地模型，并校验来源与忠实性；
- 维护四个 artifact slot，隔离失败并原子替换结构化 current；
- 对 faithful AI 失败执行已声明的确定性规则 fallback。

Pipeline、desktop worker、CLI、UI controller 和 `document` 都不得复制这些规则。测试也通过这两个
入口验证可观察行为，不把私有 chunk helper 或文件布局变成新的公共 seam。

### 2. 新任务只冻结一个初始计划

v0.5.0 新 Job 在创建时带显式 `ContentSetupV1` marker；缺少该 marker 的任务是 legacy：

```text
ContentSetupV1
├── schema_version = 1
├── recipe_set_version
├── enhancements_requested
└── initial_target
    ├── Disabled             用户关闭 AI 增强
    ├── Ready(ReadyGenerationTargetV1) 创建时设置可用
    └── Unavailable(TargetUnavailableV1) 用户开启增强但设置不可用
```

一个 Job 只有这一个 initial target，不保存 target history，也没有 active/initial 双指针。普通设置
修改不改变已有 Job 的初始计划。

- `enhancements_requested = false`：faithful 使用确定性规则；三个增强 slot 为未请求。
- `Ready`：faithful 可以使用 AI 校正；章节、默认摘要和重点使用同一冻结目标分别生成。
- `Unavailable`：任务仍可创建；faithful 使用规则 fallback，三个已请求增强分别保存可行动失败。

用户修好设置后，只能从终态 v0.5 Job 明确点击“使用当前 AI 设置重新生成摘要/章节/重点”。
`execute(Regenerate)` 当场校验传入的设置；无效设置不写文件、不发网络请求。有效设置只属于
这次操作，成功时随新 record 保存；它不修改 initial target，也不建立 target history。普通单项
重新生成同样读取并冻结操作当下的有效设置，界面不提供模型选择器。

### 3. 本地、无鉴权的生成目标

`ReadyGenerationTargetV1` 只描述真正会发送的非敏感信息：

```text
ReadyGenerationTargetV1
├── provider             openai_compatible | anthropic_compatible
├── api_format           openai_chat_completions | anthropic_messages
├── normalized_endpoint
├── model
└── parameters
```

v0.5.0 production adapter 只接受本机、无鉴权 endpoint：scheme 为 `http` 或 `https`，host 是精确
`localhost`、`127.0.0.1` 或 `[::1]`。不得靠 DNS 解析或后缀匹配把
其他 host 判断为本机；含 userinfo、query、fragment、认证配置、空 model 或不支持协议的设置均
为 `Unavailable`。adapter 不发送认证头。

endpoint 规范化顺序固定为：去除首尾空白；以 URL parser 规范化 scheme/host 大小写并去掉默认
端口；去掉尾部斜杠；再至多去掉一个精确末尾 suffix（`/v1/chat/completions`、`/v1/messages`
或 `/v1`）。adapter 只在该 base URL 后追加自己的消息路径。v0.5.0 不增加参数 UI，实际默认值
固定为：

- OpenAI Chat Completions：`temperature = 0.2`，不发送 max output tokens；
- Anthropic Messages：发送 `max_tokens = 4096`，不发送 temperature。

provider、api format 与 typed parameter variant 只允许这两组一一对应组合；交叉组合按
`protocol_unsupported` 在网络前拒绝。

这些实际参数同时进入成功 record。密码、认证头、原始私密 URL 和完整请求体不得持久化。
`TargetUnavailableV1` 只保存脱敏 code（`connection_missing | protocol_unsupported |
endpoint_invalid | model_missing`）、短 message 和无效字段名，固定判断优先级为 connection →
protocol → endpoint → model。

### 4. 一个结构化 current 文件

每个 v0.5 Job 的 work dir 只有一个内容事实文件：`content-current.v1.json`。记录内联保存，不再
拆出 record 文件或 current pointer：

```text
ContentCurrentV1
├── schema_version = 1
├── job_id
├── evidence
│   ├── identity
│   ├── platform | bvid | page | cid | duration_ms
│   ├── raw_sha256
│   └── utterance_count
├── source_context
│   ├── main_title
│   ├── part_title?
│   └── terms[]
├── setup
│   ├── recipe_set_version
│   ├── enhancements_requested
│   └── initial_target                  Disabled | Ready | Unavailable
└── slots
    ├── faithful_text: ArtifactSlotV1
    ├── chapters: ArtifactSlotV1
    ├── default_summary: ArtifactSlotV1
    └── highlights: ArtifactSlotV1

ArtifactSlotV1
├── current?: DerivationRecordV1
└── last_failure?: DerivationFailureV1
```

增强是否请求由 `setup.enhancements_requested` 推导；slot 只表达无 current、有失败或有 current。
文件不保存
`queued`、`running`、command、attempt 或 projection 活动；重新生成中的状态只存在于当前桌面
进程的 worker/UI 内存中。

文件存在即表示 Initial 已收敛：faithful 必须有 current；未请求增强时三个增强 slot 全空；已请求
时每个增强至少有 current 或 last_failure。已发布文件中不允许 requested slot 同时缺少两者。

每个 slot 的 `revision` 从 1 开始，只在成功替换 current 时递增。失败保留旧 current 并更新
`last_failure`；成功清除旧失败。旧 revision 被丢弃，因为 v0.5.0 不提供历史、回滚或缓存复用。
revision 只属于模块内部事实。单进程、单 worker 是唯一写入边界；调用者不读取或提交 revision，
重复点击由内存 busy 门禁拒绝。

### 5. 成功 record 保留完整而可读的追溯信息

```text
DerivationRecordV1
├── schema_version = 1
├── kind
├── revision
├── evidence_identity
├── source_context
├── provenance
│   ├── recipe_id + recipe_version
│   ├── prompt_id + prompt_version | none
│   ├── rules_id + rules_version
│   ├── provider | api_format | endpoint | model | none
│   ├── parameters                       none | OpenAiChatCompletions{temperature=0.2} | AnthropicMessages{max_tokens=4096}
│   ├── effective_path                   rules | llm | rules_fallback
│   └── fallback_reason?                 target_unavailable | generation_failed | response_invalid
├── blocks[]
│   ├── id | role | title? | text
│   ├── source_refs[]                   utterance id 与时间范围
│   └── source_status                   mapped | limited
├── validation
│   ├── processed_utterance_count
│   ├── total_utterance_count
│   ├── processing_coverage_complete
│   ├── record_source_status
│   └── checks[]
└── created_at
```

每项 record 都保存 PRD 要求的 provider、model、实际参数、提示/模板版本、规则版本和输入
Evidence identity。规则路径用显式 `none`/`rules` 表达没有 provider 或 prompt，不能靠缺字段猜测。
faithful fallback 记录 `rules_fallback`、实际规则版本和脱敏 fallback reason，不能把规则结果伪装成
AI 校正，也不能把运行失败误写成“配置不可用”。

`evidence_identity` 是 `EvidenceIdentityMaterialV1` 的 SHA-256：固定 domain
`bimyscribe/evidence/v1`，并依次包含 `job_id/platform/bvid/page/cid/duration_ms/raw_sha256/
utterance_count`；按声明顺序序列化为 compact UTF-8 JSON，空值不得与缺字段互换。路径、mtime 和
locale 不参与。v0.5.0 不增加 derivation key、recipe digest 或 attempt identity；没有缓存和历史
时，可读 provenance 与 slot revision 已足以追溯。加载时复核 schema、Job、Evidence descriptor、
raw SHA、block id 和引用边界；current 缺失/损坏但 raw 有效时返回 `RawOnly`，不从 Markdown
修复。只有显式 `Initial`（由正常 Pipeline、其 Retry 或 `RepairContent` 调用）才可完全从 raw
重建并原子替换损坏 current；普通 open/load 不产生写入。

### 6. 四项产物直接以 Evidence 为根

faithful、chapters、default summary 和 highlights 都直接读取同一份 Evidence。某次执行可以在
模块内部共享分块结果，但另一项用户可见产物不是必需前置条件；重新生成章节不会运行摘要，
重新生成摘要也不会改写 faithful。

模块按连续 utterance 与时间范围切块，记录每个输入 chunk 是否进入最终 merge。
`processing_coverage` 证明完整输入经过处理；可见 block 的 `source_refs` 只证明该结论由哪些片段
支持，两者不可混用。summary/highlights 可以只引用被选中的片段，但其生成过程仍必须覆盖全部
输入。至少拒绝以下候选：

- 未解释的输入缺口、后半段丢失或异常重复；
- 空结果、空章节、章节乱序或超出 Evidence 的时间范围；
- 引用不存在、越界或与 block 不一致的 utterance；
- faithful 的删除、幻觉、数字/链接损坏、错序或异常压缩。

`mapped` block 有一个或多个通过校验的 refs，可以展开原始片段并生成时间链接。`limited` block
可以诚实展示文本，但 refs 为空、必须显示“来源受限”，且不得合成精确链接。零 refs 只允许在
`limited`；任何已经提供但不存在、越界、倒序或 source unit 不匹配的 ref 都使候选失败。一个
record 含任一 limited block 时，其汇总状态为 limited。

faithful 的 AI 候选若请求、解析或忠实性校验失败，使用确定性规则生成 mapped fallback 并留下
warning；fallback 也必须保持全输入顺序和逐段 Evidence refs。章节、摘要或重点失败时不伪造
规则结果，只更新各自的 `last_failure`。

### 7. 初始执行与单项重新生成

`Initial` 在 Pipeline 已持久化并验证 Evidence 后执行四项计划。它在内存中形成一个完整
snapshot，四项都收敛后才用一次 whole-file replace 发布；取消、崩溃或 faithful fatal 不发布
半成品，也不向 UI 暴露“尚未生成”的中间 slot。各增强失败是非致命结果，faithful 成功后
Pipeline 可以带 warning 收敛为 Completed。若 faithful 本身无法形成有效规则结果，内容阶段失败。

Pipeline retry 遇到 Evidence identity/setup 匹配且结构有效的 `content-current.v1.json` 时复用
所有已有 current，只重新尝试已请求且仍无 current 的增强项；若进程在第一次发布前退出，没有
可恢复 attempt，重试会重新执行完整 Initial，可能重复本地模型调用。
缺失或损坏 current 不在 open/load 时修复；显式 `Initial` 从已验证 raw 构造完整候选，并只在
最终原子替换点覆盖旧文件。

`Regenerate` 只允许 terminal v0.5 Job 的 chapters、default summary 或 highlights：

- 使用既有 `transcript.raw.json`，metadata、下载、FFmpeg 和 ASR 调用次数必须为零；
- 同一 desktop worker 串行执行；忙时其他重新生成按钮禁用，不持久排队；
- Job 的 Completed/Failed/Cancelled 终态不因该操作改变；
- 成功只替换目标 slot；失败保留旧 current，其他 slot 永不改变；
- 进程崩溃或取消时旧 current 保留，重启后不自动续跑，用户可以再次点击。

`RawOnly` 使用独立的内存 `RepairContent` 消息，而不复用只面向 Failed/NeedsUserAction 的现有
Pipeline Retry。它只接受 raw 有效、worker 空闲的 terminal v0.5 Job；Completed、Failed、
Cancelled 均可。worker 保持原 status、stage 和 finished_at，直接执行 `Initial` 并重建
Presentation；metadata、下载、FFmpeg 和 ASR 调用次数为零。修复期间不开放三个单项
Regenerate。`Initial` 原子发布前失败、取消或退出仍为 RawOnly；发布后即为 Current，随后
Presentation 失败只产生文档 warning，不能回滚 current。消息不持久化，提交前退出后由用户
再次点击；raw 本身无效时不提供结果入口，任务详情明确要求重新创建任务。

这个模型明确不提供 exactly-once。极少数崩溃可能导致本地模型已经收到请求但结果未提交；
个人工具接受人工 retry 和可能重复调用，不为此建立 receipt 或 tombstone。

### 8. whole-file 原子替换

`ContentResults` 在同一 work dir 写临时文件，flush/fsync 后重新读取并完成 schema、Evidence、slot
与引用校验，再 rename 覆盖 `content-current.v1.json`，最后 fsync 父目录。rename 是提交点：此前
任一步失败都保持旧 current；此后新 current 已可见，父目录 fsync 失败只能记录 durability
log warning 并返回新 snapshot，不能声称旧文件仍在或回滚。`current()` 只忽略无主临时文件且零写；
显式 `execute` 或既有启动 recovery 可以 best-effort 清理，但绝不提升它们。

个人工具的单 Job current 很小，整个 JSON 重写比 record ledger 更容易验证和维护。模块假设一个
BiMyScribe 进程、一个 worker 串行写同一 Job；不支持多进程共享队列或并发 writer。

### 9. App 与 Markdown 的消费方式

结果视图直接调用 `current(job)`，再用 snapshot 内的 validated Evidence view 展示来源。结果入口
只在 v0.5 Job 已进入 terminal 状态且原始 Evidence 有效时出现；faithful/current 缺失或损坏时
降级为只显示原始稿的壳并显示“修复文字结果”，不从 Markdown 修复。初始 Pipeline 运行中继续
使用现有任务详情和取消操作，不新增渐进结果协议。

`document` 使用同一个 renderer，从 Job display metadata、当前 speaker map 与
`ContentSnapshotV1`（其中已包含 validated Evidence view）构建 Presentation；renderer 不另读 raw：

- `transcript.raw.md` 继续由 Evidence 生成；
- `transcript.readable.md` 只由 faithful current 生成；
- v0.5 Job 只有一个最终 `full.md` 出口，不再维护 work-dir/final-output 两份镜像；
- `full.md` 包含原始/忠实/结构化/AI 标签、来源状态和精简 provenance；只有 mapped refs 生成链接。

初始生成、单项重新生成和 v0.5 speaker rename 都复用这个 renderer。文件使用普通原子替换，但
不建立 desired/applied/dirty/claim 投影状态机。App 内结构化 current 始终是事实源；打开或导出
Markdown 前重新从 current 构建，失败时不打开旧文件，而显示具体 I/O 原因和再次尝试动作。
speaker rename 已保存但文件重建失败时，同样保留结构化结果并允许再次构建；v0.5.0 不承诺跨
多个展示文件的事务式 exactly-once。

所有 v0.5 保留策略都保留 `transcript.raw.json` 和 `content-current.v1.json`，因为单项重新生成和
来源展开依赖它们。可以继续清理可下载媒体和临时文件。

### 10. GenerationPort 是唯一内部 seam

模型协议是真正变化的依赖。`ContentResults` implementation 内部保留一个 `GenerationPort`；
production 有 OpenAI Chat Completions 和 Anthropic Messages 两个 adapter，测试有一个确定性 fake
adapter。这个 seam 不暴露给 Pipeline 或 UI。

adapter 接受已经冻结的 typed request，只负责协议 envelope、HTTP 调用、响应解析和脱敏错误：
它不读取全局 Config、不选择默认参数、不改变 recipe，也不吞掉批次失败。分块、回退、来源与
完整性判断都留在 `ContentResults`，保证修复一次即可覆盖初始生成和重新生成。

### 11. Legacy 完全 passthrough

缺少 `ContentSetupV1` marker 的升级前 Job 不创建 `content-current.v1.json`，不扫描 raw JSON 进行
迁移，也不从 `full.md`/`transcript.readable.md` 反推结构化内容。它不显示 v0.5 结果入口或重新
生成操作。

旧任务继续走 v0.4.1 已有的打开 Markdown、访达中显示、Retry、恢复和 speaker rename 行为，
包括已有文件优先级与兼容路径。v0.5.0 不为旧任务增加 migration、legacy transaction 或历史
投影协议。

## 明确删除的复杂度

本 ADR 不建立以下能力，后续实现不得以“恢复完整性”为由悄悄加入：

- receipt、tombstone、attempt/command ledger 或 exactly-once；
- immutable record 文件、committed heads、current pointer、历史 revision 或缓存；
- generation target history、active target、repair transaction 或双 target 指针；
- `queue.json`/`state.json` generation CAS、split-brain 合并或 bootstrap 协议重构；
- Presentation desired/applied/dirty/claim 状态机和双 `full.md` 镜像；
- SpeakerEdit 事务 ledger；
- legacy 自动迁移或从展示文件提升内容事实；
- 通用工作流引擎、provider registry 或每项只转发一次调用的浅模块。

如果未来出现多进程 writer、远程计费模型、结果历史或跨设备同步等真实需求，再以新 ADR 根据
实际故障成本引入相应机制；v0.5.0 不为假设需求预付复杂度。

## 验证策略

- 用临时目录和固定 Evidence fixture 跨 `execute/current` interface 覆盖四项成功、部分失败、
  rules-only、Unavailable、一次 Initial 原子替换与内部 slot revision。
- 用确定性 fake adapter 覆盖标题/分 P/邻近片段/术语上下文、processing coverage、mapped/limited、
  引用越界、后半段丢失、重复、空结果、异常压缩及 faithful fallback。
- adapter envelope fixture 固定 OpenAI `temperature=0.2`、无 max tokens，以及 Anthropic
  `max_tokens=4096`、无 temperature；远程、带鉴权或畸形 endpoint 必须零网络请求。
- Pipeline 计数测试证明单项重新生成只读取既有 Evidence，metadata、下载、FFmpeg、ASR 和其他
  artifact 调用均为零；失败和进程中断不覆盖旧 current。
- Presentation 测试证明 App 与 Markdown 使用同一 current，只有 mapped refs 生成时间链接，
  `full.md` 只有一个出口，重新生成与 speaker rename 不丢失其他 section。
- legacy fixture 证明升级前 Job 字节和现有打开/reveal/rename 行为不被迁移逻辑改变。

## 非目标

- 层级大纲、多摘要深度、复杂模板、按内容类型选择模板或自定义提示；
- 在结果页选择或更换模型、provider 市场、远程鉴权服务；
- 翻译、视觉资产、OCR、全文搜索和新的导出编辑器；
- 把生成内容写回 Evidence，或以另一项派生产物作为不可见强依赖；
- 多进程并发写、远程任务队列、生成历史、回滚和 exactly-once。

## 结果与取舍

- `ContentResults` 以两个入口隐藏内容生成、校验和持久化，减少 Pipeline、UI 与 `document` 的
  interface 知识，提高 locality。
- 单一 whole-file current 不能提供历史或自动续跑，但故障边界清楚：旧 current 保留，用户重试。
- 初始发布前崩溃可能重复本地模型调用；这是单机个人工具可接受的成本。
- 四项都从 Evidence 生成会重复部分计算，但保证失败与重新生成互不耦合。
- Architecture 1.2 已记录上述 v0.5 当前实现边界；交付状态以路线图为准，版本内容以版本化
  Release Notes 为准。公开发布前仍需遵循版本、验收与发布门禁。
